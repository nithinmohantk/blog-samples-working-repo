A request to put generative AI in front of Irish health service staff usually arrives as one sentence: train a model on our data. In an Irish healthcare setting that sentence covers three different things, and Amazon Bedrock treats each one differently. Published guidance, such as HIQA's National Standards for Information Management in Health and Social Care and HSE national policies, is knowledge that changes with every new edition. How the assistant answers (its format, its citations, when it refuses) is behaviour. Patient identifiers and records are data that must not reach a model at all.

This article argues that each of the three needs its own route. Knowledge belongs in a Bedrock Knowledge Base in eu-west-1, the Dublin Region, where a new edition is a document update rather than a training run. Fine-tuning is reserved for behaviour, and only on synthetic or published non-personal examples, because Bedrock runs customisation for Amazon Nova models in US Regions and the training set crosses a border. Individual Health Identifier (IHI) values and PPS numbers are blocked twice: by a gate in front of every training set, and by a Guardrail in front of every question. A release pipeline then decides whether a change reaches users, using a golden set, deterministic scores and a named clinical safety officer.

The sections below cover the Region constraints that shape the design, the Knowledge Base corpus, identifier detection, the fine-tuning path, the evaluation gate and the Step Functions pipeline, followed by cost, production concerns and a decision framework. A tested Python sample implements the gates.

Scenario

The assistant answers questions from health service staff about published information governance guidance: what to record when information is shared, how the IHI field is populated, when a privacy impact assessment is needed. Its corpus is HIQA standards, HSE national policies and Department of Health publications. It is not clinical decision support. It does not see patient records, and a question about an individual patient is refused.

That scope is deliberate. An assistant that drafts discharge summaries or suggests doses carries a different clinical risk and a different regulatory classification, and the gates described here would be necessary but nowhere near sufficient.

ℹ️
SCOPE AND ASSUMPTIONS

Users are authenticated staff. The corpus is published, non-personal documents. Answers must cite the document and edition they came from. Data stays in the EU unless a documented decision says otherwise. The sample uses synthetic data only and the pattern is not clinically validated.

Requirements

Region constraints

Region support decides the architecture, so it comes first. The Bedrock user guide's table of models that can be fine-tuned lists only us-east-1 and us-west-2. The Nova understanding models (Micro, Lite and Pro) are customised in us-east-1, and the Llama models in us-west-2. On-demand inference for a custom Nova model is also listed for us-east-1 only. The model copy table lists eu-west-1 as a destination for customised Nova Micro, Lite and Pro, but copying a model is not the same as serving it on demand, and Provisioned Throughput for custom models is sold with a commitment or, without one, at an hourly rate with a limit of two per account.

The Knowledge Base side is different. Titan Text Embeddings V2 is listed for Knowledge Bases in eu-west-1, as are both Cohere Embed v3 models, and Bedrock Guardrails is available in eu-west-1. Retrieval and safety checks can therefore run in Dublin, and generation can use a base model offered in eu-west-1 or an EU geographic inference profile, which routes requests only to EU Regions.

The consequence is a simple rule: anything that has to stay in the EU goes into retrieval, and only data with no personal content can go into training. A model trained in the US on synthetic examples of citation style and refusal wording raises no data transfer question. A model trained on ward notes would, even with a transfer mechanism in place, and it would also hold that content in its weights where it cannot be deleted.

⚠️
IDENTIFIERS IN WEIGHTS

A record that reaches a training job cannot be withdrawn from the resulting model. Removing it means deleting the custom model and training again from a clean set. That is why the identifier check sits in front of the training job, and why it is deliberately broad.

A question passes through the Guardrail, then RetrieveAndGenerate retrieves passages from current editions only and generates an answer with a model in the EU Region. The corpus reaches the Knowledge Base through a corpus gate. The fine-tuning path is separate. It produces a candidate model, and that candidate goes through the same release gate as a prompt change or a re-chunked index before it can answer anyone.

Knowledge Base corpus

Most of the value is in the corpus, not the model. Each source document in S3 gets a sidecar file named after it with .metadata.json appended, which Bedrock Knowledge Bases reads at ingestion and can filter on at query time. The sample records publisher, version, publication date and a status computed from the review date and any superseding document.

def sidecar(doc: SourceDocument, as_of: date) -> dict:
    """Content of `<file>.metadata.json` for an S3 data source."""
    return {
        "metadataAttributes": {
            "doc_id": doc.doc_id,
            "title": doc.title,
            "publisher": doc.publisher,
            "version": doc.version,
            "published": doc.published.isoformat(),
            "published_year": doc.published.year,
            "status": doc.status(as_of),
        }
    }

When HIQA publishes a new edition, the old file stays in the bucket for history, its manifest entry gains superseded_by, and the next ingestion marks it superseded. Every query carries a filter that excludes it, so retrieval changes without a model change:

def current_documents_filter() -> dict:
    """Retrieval filter: current editions from approved publishers only."""
    return {
        "andAll": [
            {"equals": {"key": "status", "value": "current"}},
            {"in": {"key": "publisher", "value": sorted(PUBLISHERS)}},
        ]
    }

The corpus gate also refuses a document from a publisher not on the allow list, a document past its review date, and a document whose text contains an identifier. The last check exists because published PDFs occasionally contain worked examples with realistic-looking numbers.

Chunking matters more for standards documents than for most corpora. A standard and its supporting features are only meaningful together, so semantic or hierarchical chunking usually beats fixed-size chunks. Choose the chunking strategy with the evaluation gate, not by inspection, because the gate measures what the reader actually sees: whether the right document is cited.

Identifier detection

The HSE National Policy for IHI Data Standards defines the IHI as an 18-digit GS1 Global Service Relation Number, with a 10-digit human-friendly form. The field is populated from the IHI index and is not typed in. A PPS number is seven digits followed by one or two letters, the first of which is a check character. Both have published check algorithms: GS1 modulo 10 for the GSRN, and modulus 23 for the PPSN.

def gs1_check_digit_ok(digits: str) -> bool:
    """GS1 modulo-10: weights 3,1,3,... from the digit left of the check digit."""
    if not digits.isdigit() or len(digits) < 2:
        return False
    body, check = digits[:-1], int(digits[-1])
    total = sum(int(d) * (3 if i % 2 == 0 else 1) for i, d in enumerate(reversed(body)))
    return (10 - total % 10) % 10 == check


def ppsn_check_ok(number: str) -> bool:
    """Modulus 23 check character, weights 8..2 on the digits.

    Since 2013 a second letter A or H also carries weight 9 (A=1 ... H=8).
    A remainder of 0 maps to W.
    """
    m = re.fullmatch(r"(\d{7})([A-W])([A-Z]?)", number.upper())
    if not m:
        return False
    digits, check, second = m.groups()
    total = sum(int(d) * w for d, w in zip(digits, range(8, 1, -1)))
    if second in ("A", "H"):
        total += (ord(second) - 64) * 9
    expected = "W" if total % 23 == 0 else chr(64 + total % 23)
    return check == expected

The detector reports a match whether or not the check digit is valid. A mistyped identifier is still an identifier. The check only labels the finding, so that a reviewer can see whether a number is very likely a real IHI or just an 18-digit number. In the sample, the PPSN check agrees with the python-stdnum library on 5,000 random numbers, and the GS1 check matches GS1 UK's worked example.

Bedrock Guardrails has built-in sensitive information types, and the list in the botocore service model includes UK NHS numbers but no Irish identifiers. IHI and PPSN therefore become custom regex entities. Guardrail regexes do not support lookaround, so the patterns are simpler than the Python detector, which is acceptable because they only need to block.

"regexesConfig": [
                {"name": "ihi-gsrn", "description": "Individual Health Identifier, 18 digits",
                 "pattern": r"\b\d{18}\b", "action": "BLOCK"},
                {"name": "ihi-short", "description": "Individual Health Identifier, 10-digit form",
                 "pattern": r"\b\d{10}\b", "action": "BLOCK"},
                {"name": "ppsn", "description": "Personal Public Service Number",
                 "pattern": r"\b\d{7}[A-Wa-w][A-Za-z]?\b", "action": "BLOCK"},
            ],

The ten-digit pattern also matches Irish mobile numbers. In this assistant that is a feature: no answer needs a phone number either. The Guardrail also denies one topic, patient-specific clinical advice, and applies contextual grounding checks so that an answer the retrieved passages do not support is withheld.

Fine-tuning

Fine-tuning is worth doing when the evaluation gate shows that prompting cannot get the base model to behave consistently: citing every statement, using the house answer structure, refusing in the right words, preferring Irish terminology. It is not the way to teach the model what the 2024 standards say. Knowledge put into weights goes stale with the next edition and cannot be cited back to a page.

Training records use the Bedrock conversation format (schemaVersion set to bedrock-conversation-2024, an optional system prompt, alternating user and assistant turns). The Nova documentation recommends at least 100 samples per task. The dataset gate in the sample adds three rules of its own. Every record declares a provenance from an allowed list (synthetic, author-written, or published HIQA or HSE text). No record contains an identifier. And the gate writes a certificate holding the SHA-256 of the exact file it approved, with the metadata stripped.

def submit_customization(bedrock, settings: Settings, certificate: dict, dataset: Path,
                         train_s3_uri: str, job_name: str, hyperparameters: dict[str, str]) -> str:
    region = bedrock.meta.region_name
    if region not in settings.training_regions:
        raise PolicyError(f"{region} is not an approved training Region")
    if certificate.get("personal_data") is not False:
        raise PolicyError("certificate does not state the dataset is free of personal data")
    digest = hashlib.sha256(dataset.read_bytes()).hexdigest()
    if digest != certificate.get("dataset_sha256"):
        raise PolicyError("dataset changed after it passed the gate")
    check_hyperparameters(hyperparameters)

    response = bedrock.create_model_customization_job(
        jobName=job_name,
        customModelName=f"{job_name}-model",
        roleArn=settings.role_arn,
        clientRequestToken=digest[:32],          # same dataset, same job: retries are safe
        baseModelIdentifier=settings.base_model_id,
        customizationType="FINE_TUNING",
        customModelKmsKeyId=settings.kms_key_arn,
        trainingDataConfig={"s3Uri": train_s3_uri},
        outputDataConfig={"s3Uri": settings.output_s3_uri},
        hyperParameters=hyperparameters,
        jobTags=[{"key": "dataset-sha256", "value": digest}, {"key": "personal-data", "value": "none"}],
    )
    log.info("customization job started", extra={"job_arn": response["jobArn"], "region": region})
    return response["jobArn"]

The wrapper refuses to start a job in any Region outside the approved training list, refuses a file whose hash differs from its certificate, and checks hyperparameters against the documented ranges for Nova understanding models: epochCount 1 to 5, learningRate 1e-6 to 1e-4, learningRateWarmupSteps 0 to 100. Nova does not expose batchSize, so passing it is a configuration error rather than a silent no-op. The client request token is derived from the dataset hash, so a retried submission of the same file does not start a second paid job.

⚖️
GDPR AND THE HEALTH IDENTIFIERS ACT

Health data is special category data under Article 9 GDPR, and moving it to a US Region is a Chapter V transfer. The design avoids both questions by keeping personal data out of training entirely. The Health Identifiers Act 2014 governs the use of the IHI and its national register (section 11); read it with your data protection officer before any record that carries an IHI goes near a model or a log.

There is an EU-only route if behaviour tuning is unavoidable and the training data cannot leave the EU: fine-tune an open-weights model in SageMaker AI in an EU Region, then bring it into Bedrock with Custom Model Import, which is listed for eu-central-1 (Frankfurt). It costs more engineering. Imported models cannot be used with batch inference or CloudFormation, and the training pipeline becomes yours to run.

Evaluation gate

Every change that can alter an answer is a candidate: a new custom model, a prompt template, a chunking change, a new Guardrail version, a corpus refresh. The gate asks a golden set of questions through the candidate configuration and scores the recorded answers. The golden set has three kinds of item: questions it should answer, with the documents it should cite and phrases the answer must contain; questions it should refuse, such as a dose for a described patient; and identifier probes, which contain or ask for an IHI.

Scores are deterministic: source recall against the expected documents, citation precision against current documents only (so a citation of a superseded edition counts against the candidate), coverage of required phrases, refusal accuracy, identifier leaks and p95 latency. Bedrock's RAG evaluation, generally available since March 2025, adds LLM-as-a-judge metrics such as faithfulness, citation precision and citation coverage. Those are a useful second opinion in the report, but the release decision should not depend on a judge model whose own behaviour can change between runs.

def decide(candidate: Scores, production: Scores | None) -> tuple[bool, list[str]]:
    reasons: list[str] = []
    if candidate.identifier_leaks:
        reasons.append(f"BLOCK identifier leaks: {candidate.identifier_leaks}")
    if candidate.missing_answers:
        reasons.append(f"BLOCK missing answers: {candidate.missing_answers}")
    for metric, floor in THRESHOLDS.items():
        value = getattr(candidate, metric)
        if value < floor:
            reasons.append(f"BLOCK {metric} {value:.3f} below {floor:.2f}")
    if candidate.p95_latency_ms > LATENCY_BUDGET_MS:
        reasons.append(f"BLOCK p95 latency {candidate.p95_latency_ms} ms over {LATENCY_BUDGET_MS}")
    if production is not None:
        for metric, tolerance in TOLERANCE.items():
            drop = getattr(production, metric) - getattr(candidate, metric)
            if drop > tolerance:
                reasons.append(f"BLOCK {metric} regressed by {drop:.3f} (tolerance {tolerance})")
    return (not reasons, reasons)

An identifier leak blocks on its own, whatever the other scores. The floors catch a candidate that is bad in absolute terms, and the tolerances catch one that is acceptable but worse than what is in production. Both matter, because a golden set of forty questions where production scores 0.97 should not accept a candidate at 0.91 just because 0.91 clears the floor.

Release pipeline

A Step Functions state machine runs the gates in order. If the change includes a training set, it runs the dataset gate, starts the customisation job and polls it. It then validates the corpus, starts a Knowledge Base ingestion job and polls it, asks the golden set through the candidate and scores it. A candidate that passes waits for a clinical safety officer, using an SNS message with a task token.

The approval step has a seven-day timeout. A timeout or a rejection goes to the same reject path as a failed gate, so a candidate cannot reach production by being ignored. Promotion writes the candidate configuration to an SSM parameter that the application reads. SSM keeps parameter history, so rollback is a write of the previous version and needs no redeployment.

The sample's asl_lint.py checks the definition without AWS: every Next names a state, every Choice has a Default, no state is unreachable, and every path from the start to PromoteAlias passes through the corpus check, the evaluation decision and the sign-off. A test changes one Choice to jump straight to promotion and confirms the lint catches it. This is the kind of shortcut a well-meaning change introduces at the end of a long day.

Cost

The two routes have different cost shapes. The retrieval-only route is usage-priced: embedding at ingestion, the vector store, Guardrail text units per call and model tokens per answer. Nothing has to be committed in advance, and a corpus refresh costs an ingestion job.

The fine-tuning route adds a training charge that grows with dataset size and epoch count, because each epoch processes the whole set again. It also adds the cost of serving the custom model. On-demand inference for custom Nova models is listed only in us-east-1, which puts generation in the US. Serving in another Region means Provisioned Throughput, sold with a one-month or six-month commitment, or without commitment at an hourly rate (at most two per account). For a staff guidance assistant with office-hours traffic, that commitment is usually the deciding factor. Price both routes from the Bedrock pricing page for your Region and expected volume before choosing.

The evaluation gate has a cost of its own: every candidate asks the full golden set. At forty to a few hundred questions that is small next to a training job, and it is the cost that stops an expensive mistake from reaching users.

Production considerations

  • Logging. Enable Bedrock model invocation logging to a bucket and log group in eu-west-1, encrypted with a customer-managed KMS key. Log Guardrail assessments with masked values only, and never write raw questions to application logs: a user will paste an identifier sooner or later.
  • Monitoring. Alarm on the Guardrail intervention rate, on answers with no citation, on retrievals that return nothing, and on p95 latency. A rise in uncited answers usually means the corpus or the filter has drifted, not the model.
  • Access. Separate IAM roles for the training Region and the data Region. The training role can read only the certified dataset prefix, and the application role cannot call any customisation API.
  • Resilience. The Knowledge Base can be rebuilt from the S3 corpus and manifest, which are versioned. The active configuration is a parameter with history. Record recovery time and recovery point objectives in the service's runbook alongside the ingestion time for the full corpus.
  • Freshness. Review dates live in the manifest, and the corpus gate fails when one passes. A failed nightly check is a prompt to the content owner, not to engineering.
  • Clinical safety. Keep a hazard log for the assistant even though it is scoped away from clinical decisions. Refusal failures and citation of superseded guidance belong in it, with the golden set items that test each one.

As of 20 June 2026, the Digital Omnibus on AI has been provisionally agreed and voted by the European Parliament. It would move high-risk obligations to 2 December 2027 for Annex III systems and 2 August 2028 for systems in Annex I products such as medical devices. Until it is published in the Official Journal, 2 August 2026 remains the legal date. An information governance assistant is unlikely to be high-risk, but the classification should be recorded, and it changes if the assistant is ever used to support clinical decisions.

Decision framework

The default is the first row. Move to the second only when the evaluation gate shows that prompting has run out, and record that evidence in the decision record. That changes if Bedrock lists on-demand custom model inference in an EU Region: the cost argument against fine-tuning then weakens, and the data argument does not change at all.

HOW THIS WAS CHECKED

The sample's 30 tests pass on Python 3.13 with boto3 and botocore 1.43.34, pytest 9.1.1 and python-stdnum 2.2, resolved as of 19 June 2026. The Bedrock requests are checked with botocore's Stubber, which validates them against the service model; one test confirms it rejects a misspelt key. Nothing ran against AWS: no customisation job, Knowledge Base, Guardrail or state machine was created, and the answers scored by the evaluation gate are hand-written fixtures, not model output. The corpus files are hand-written stand-ins for the HIQA and HSE documents. Region support comes from the Bedrock user guide's Region tables, which change; check them again before you build. The state machine was linted but not deployed.

Key takeaways

  • Published guidance belongs in a Knowledge Base in eu-west-1, filtered to current editions, not in model weights.
  • Bedrock customises Nova models in US Regions, so a training set must contain no personal data, and a gate should prove it with a hash-bound certificate.
  • IHI (18-digit GSRN or 10-digit form) and PPSN need custom Guardrail patterns; the built-in types do not cover them.
  • Every change is a candidate that faces the same golden set, deterministic scores and a regression check against production.
  • A named clinical safety officer approves promotion, and an ignored approval request expires as a rejection.

Glossary

Amazon Bedrock Knowledge Bases
Managed retrieval augmented generation (RAG): ingests documents from S3, embeds them, and retrieves passages for a model to answer from.
RetrieveAndGenerate
Bedrock Agent Runtime API that retrieves from a Knowledge Base and generates a cited answer in one call.
Metadata sidecar
A .metadata.json file stored beside a source document whose attributes can be used to filter retrieval.
Supervised fine-tuning
Further training of a base model on labelled input and output pairs to change how it responds.
Bedrock Guardrails
Configurable input and output checks: denied topics, sensitive information filters with custom regex, and contextual grounding.
Contextual grounding check
A Guardrail filter that withholds an answer the retrieved passages do not support.
IHI
Individual Health Identifier, assigned under the Health Identifiers Act 2014; an 18-digit GS1 GSRN with a 10-digit display form.
GSRN
GS1 Global Service Relation Number: an 18-digit identifier whose last digit is a modulo 10 check digit.
PPSN
Personal Public Service Number: seven digits and one or two letters, the first a modulus 23 check character.
Golden set
A fixed, versioned set of questions with expected sources and behaviours, asked through every candidate.
Provisioned Throughput
Dedicated Bedrock model capacity bought in model units, with or without a commitment term.
Custom Model Import
Bedrock feature that brings externally trained open-weights models into Bedrock for inference.
Task token
A Step Functions token that pauses a state until an external party calls SendTaskSuccess or SendTaskFailure.
