For eleven years GraphQL ran over HTTP on conventions. The 2016 "Serving over HTTP" page on graphql.org said roughly how to send a query, and everyone filled in the rest: most servers answered 200 OK for everything, errors included, because a non-200 status might have come from a proxy rather than from GraphQL. Monitoring tools could not tell a failed query from a successful one without reading the body.

On 12 November the GraphQL Technical Steering Committee published the first edition of the GraphQL over HTTP specification, named the September 2026 edition. It adds a media type, application/graphql-response+json, and with it a full set of status codes, including a new 294 Partial Success. I ran six popular servers with their default settings against it, sent each the same 22 requests, and compared the answers with the text. This article covers what the specification requires, which servers already follow it, and what to change in clients, servers and the infrastructure in between.

What the specification settles

The specification is a supplement to the GraphQL specification, which stays transport-agnostic. It covers the URL, GET and POST requests, JSON encoding, headers and status codes. Subscriptions are not covered; the HTTP QUERY method, persisted documents and request batching are planned for later editions.

The new media type is what makes honest status codes safe. A client that receives application/graphql-response+json knows the body is a GraphQL response whatever the status, so a 422 from GraphQL can no longer be confused with a 422 from a gateway. Clients are told to read the body and ignore the status code; the status code is for everything in between: logs, gateways, dashboards and intrusion detection.

ℹ️
WHY 294

There is no registered HTTP status for "partial success": 203, 206 and 207 each mean something else. The specification defines 294 Partial Success itself and recommends it only together with application/graphql-response+json. HTTP clients that do not know 294 must treat it as 200, but the specification warns that infrastructure with fixed lists of status codes (caches, load balancers, WAFs) may handle it differently, so test every hop.

⚠️
THE EDITION DISAGREES WITH ITSELF ON FIELD ERRORS

The Status Codes section says a result with both data and errors SHOULD get 294. The worked example "Field errors encountered during execution" a few lines later still says the server SHOULD respond 200 OK. Both are 2xx, so either is allowed; 294 is the newer intent (it was adopted in April 2026), but expect implementations to differ until an erratum settles it.

The sample's client follows that path. It sends the recommended Accept header, reads application/graphql-response+json at any status, reads application/json only on 2xx, and turns everything else into a transport error. For legacy servers that answer validation errors with 400 and application/json, there is an opt-in to read those bodies when you control every hop in front of the server.

"""A GraphQL-over-HTTP client that reads responses the way the September 2026 edition says.

- Send Accept: application/graphql-response+json, application/json;q=0.9
- application/graphql-response+json: a GraphQL response, whatever the status code.
- application/json: a GraphQL response only when the status is 2xx (legacy servers).
- Anything else (a proxy's 502 page, a rate limiter's 429): a transport error.

Servers that never send application/graphql-response+json (legacy servers) often answer a
validation error with 400 and application/json. The spec says a client cannot know such a body
came from GraphQL, so by default it is a transport error. If you know every hop in front of the
server, trust_json_errors=True reads those bodies too, when they have the shape of a GraphQL result.
"""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any

import httpx

GQL = "application/graphql-response+json"
JSON = "application/json"
ACCEPT = f"{GQL}, {JSON};q=0.9"


class TransportError(Exception):
    """The response did not come from a GraphQL server, or could not be read as one."""

    def __init__(self, status: int, content_type: str, message: str) -> None:
        super().__init__(f"HTTP {status} ({content_type or 'no content type'}): {message}")
        self.status = status
        self.content_type = content_type


@dataclass
class Result:
    data: dict[str, Any] | None
    errors: list[dict[str, Any]] = field(default_factory=list)
    extensions: dict[str, Any] | None = None
    status: int = 200

    @property
    def partial(self) -> bool:
        """Executed, with some fields failing: data and errors together (status 294 when the server follows the spec)."""
        return self.data is not None and bool(self.errors)

    @property
    def request_error(self) -> bool:
        """Not executed at all: parse, validation or variable errors."""
        return self.data is None and bool(self.errors)


class GraphQLHTTPClient:
    def __init__(self, url: str, client: httpx.Client | None = None, timeout: float = 10.0,
                 trust_json_errors: bool = False) -> None:
        self.url = url
        self._client = client or httpx.Client(timeout=timeout)
        self.trust_json_errors = trust_json_errors

    def execute(self, query: str, variables: dict[str, Any] | None = None,
                operation_name: str | None = None) -> Result:
        body: dict[str, Any] = {"query": query}
        if variables is not None:
            body["variables"] = variables
        if operation_name is not None:
            body["operationName"] = operation_name
        response = self._client.post(self.url, json=body, headers={"accept": ACCEPT})
        return self.read(response, self.trust_json_errors)

    @staticmethod
    def read(response: httpx.Response, trust_json_errors: bool = False) -> Result:
        media = response.headers.get("content-type", "").split(";")[0].strip().lower()
        status = response.status_code
        legacy_error = media == JSON and 400 <= status < 500 and trust_json_errors
        if media == GQL or (media == JSON and 200 <= status < 300) or legacy_error:
            try:
                payload = response.json()
            except ValueError as exc:
                raise TransportError(status, media, "body is not JSON") from exc
            if not isinstance(payload, dict) or ("data" not in payload and "errors" not in payload):
                raise TransportError(status, media, "body is not a GraphQL response")
            return Result(payload.get("data"), payload.get("errors") or [], payload.get("extensions"), status)
        raise TransportError(status, media, response.text[:200])

Six servers against the specification

Each server ran its default HTTP stack with the same schema: hello, user(id), a boom field that always throws (to produce partial results) and a setGreeting mutation. Versions are the newest stable releases published before 24 November: graphql-http 1.23.1 (the reference implementation in the GraphQL organisation), GraphQL Yoga 6.1.1, Apollo Server 5.5.2, Mercurius 16.12.2 on Fastify, all on graphql-js 16.15.0, and Strawberry 0.341.3 and Ariadne 1.1.1 on graphql-core 3.3.2.

Key: ✅ as specified, ⚠️ allowed but not what the specification recommends (a SHOULD), ❌ breaks a MUST, · left open. gql is application/graphql-response+json, json is application/json. D4 and D5 repeat the GET requests with Apollo's preflight header.

Three servers do not speak the new media type

graphql-http, Yoga and Apollo Server answered application/graphql-response+json when asked and fell back to application/json for a legacy Accept. Mercurius, Strawberry and Ariadne answered application/json to every request, including one that asked only for the new type. Under the new edition that makes them legacy servers: supporting the media type is a MUST. They still work for clients that send application/json;q=0.9 as a fallback, which is why the specification recommends that header.

Nobody uses 422 or 294 yet

Every server answered validation errors, ambiguous operations and bad variables with 400 (or 200), and every partial result with 200. Both recommendations are new: 422 and 294 entered the draft in April 2026, and graphql-http 1.23.1 was released on 28 September, before the edition. graphql-http's own audit suite, which tests the draft's earlier expectations, passes all 61 checks against graphql-http and Yoga. Expect status codes to change in the next releases of these libraries, and treat that as a behaviour change for dashboards and alerts.

The MUST-level findings

  • graphql-http answered a missing required variable with 200 and application/graphql-response+json, with errors and no data. A result without data MUST get a 4xx or 5xx; the same server answered a validation error correctly with 400.
  • GraphQL Yoga refused a request with an extra top-level property ("trace": true) with 400 Unexpected parameter "trace" in the request body. The specification says servers MUST ignore properties they do not understand, so that new request properties can be added later.
  • Mercurius refused a mutation over GET with 405 but sent no Allow header, which RFC 9110 requires with 405. graphql-http's audit also flagged it for rejecting "extensions": null.
  • Mercurius, Strawberry and Ariadne never send application/graphql-response+json (above).

Other behaviour worth knowing

  • Apollo Server's CSRF prevention refused every GET and the text/plain POST with 400, before looking at the operation, because a browser can send those without a CORS preflight. With its apollo-require-preflight header the same GET query succeeded and the GET mutation got 405. This is the pattern the specification's security notes describe; budget for the extra header in clients that use GET.
  • Ariadne answered GET requests with the GraphiQL page, even when the client asked for application/graphql-response+json, so it does not serve queries over GET by default. That is allowed (GET is optional), but caching proxies will not get GraphQL responses from it.
  • Strawberry answered a document that does not parse and a validation error with 200. Strawberry and Mercurius also included "data": null in request-error results; the GraphQL specification says data should not be present when an error happens before execution, and with the new status rules a data entry changes the expected status from 4xx to 294.
  • A strict client cannot read legacy validation errors. Mercurius and Ariadne answer an unknown field with 400 and application/json. A client that follows the specification cannot tell that body from a proxy's error, so it reports a transport error and the GraphQL message is lost. That is the case the client's trust_json_errors option exists for.

What to change

Key takeaways

  • The September 2026 edition makes application/graphql-response+json mandatory for servers and lets status codes carry meaning: 200, 294, 400, 422, 405, 415, 406.
  • Clients should read the media type first: application/graphql-response+json is GraphQL at any status; application/json only on 2xx.
  • Three of six servers tested already speak the media type; none uses 422 or 294 yet, not even the reference implementation released before the edition.
  • Four MUST-level gaps showed up with default settings: 200 for a result without data, refusing an unknown body property, 405 without Allow, and no support for the media type.
  • 294 is new to every proxy, CDN and dashboard; test each hop before servers start sending it.

Glossary

GraphQL over HTTP
The specification, separate from the GraphQL specification, for sending GraphQL requests and responses over HTTP; first edition September 2026.
application/graphql-response+json
The response media type that marks a body as a GraphQL response following the specification, whatever the status code.
Legacy server
A server that does not support application/graphql-response+json; it does not conform to the specification.
Legacy client
A client that only accepts application/json; servers answer it with that type on 2xx.
Request error
An error before execution (parse, validation, variable coercion, operation selection); the result has no data entry.
Execution (field) error
An error while resolving a field; the result has data, possibly with nulls, and errors.
294 Partial Success
A status code defined by the specification, not by IANA, for results with both data and errors.
Well-formed request
A request whose parameters have the right names and types; the document does not have to parse.
CSRF preflight header
A custom header, such as Apollo's apollo-require-preflight, that forces browsers to send a CORS preflight before the request.
